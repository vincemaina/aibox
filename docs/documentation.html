Documentation

aibox reference

aibox launches a disposable Docker container from any project directory, for running AI coding agents where they can edit your files but not reach your credentials.

Requirements

  • Python 3.11+ — aibox uses tomllib from the standard library.
  • Docker installed and running. Verify with docker version.
  • macOS, Linux or Windows. The container is always Linux.

Platform notes

PlatformDockerNotes
macOSDocker DesktopBind-mount ownership is translated for you.
LinuxDocker Engine or DesktopThe container's dev user is retuned to your host UID/GID at startup, so files you create stay yours.
WindowsDocker Desktop or WSL2Docker Desktop is paid for larger commercial use. WSL2 + Docker Engine is a free alternative — run aibox from inside WSL.

On Linux, Docker Engine only accepts connections from members of the docker group:

$ sudo usermod -aG docker $USER   # then log out and back in

Note: docker group membership is effectively root-level access on the host. Podman is not currently supported — its rootless UID mapping and tmpcopyup behaviour differ in ways that would silently unmask .git.

Installation

pipx is recommended for command-line tools — it keeps aibox in its own environment and still puts it on your PATH.

$ pipx install git+https://github.com/vincemaina/aibox.git

Or from a local clone, in editable mode:

$ git clone https://github.com/vincemaina/aibox.git
$ pipx install -e ./aibox

Plain pip works too:

$ pip install -e .          # runtime only
$ pip install -e ".[dev]"   # with pytest

Check it with aibox --version.

Quickstart

$ cd ~/projects/my-app
$ aibox

That resolves a stable project ID, builds the image if needed, starts an interactive container with your project bind-mounted at /workspace, applies your Git access mode, and drops you into bash as the dev user. On exit the container is removed and the volumes remain.

Global flags: --version prints the version, --help works on the top level and on every subcommand.

aibox run

Starts the container. All flags are optional and compose with .aibox.toml.

FlagArgumentDescription
-p, --portHOST:CONTAINERPublish a port. Repeatable.
-e, --envKEY=VALUESet an environment variable. Repeatable. Wins over aibox's own defaults.
--env-filePATHPass an env file to Docker. Repeatable.
--shellPATHCommand to run instead of /bin/bash.
--gitmasked · readonly · commitHow much of the host .git the agent gets. Default commit. See Git access.
--refresh—Re-fetch remote templates now rather than waiting for the 24-hour cache to expire.
--docker-argARGRaw passthrough to docker run. Repeatable.
--userUSERContainer user. Defaults to dev on macOS/Windows; on Linux the entrypoint handles the UID match.

Watch out: when a --docker-arg value itself starts with --, use the = form: --docker-arg=--add-host=host.docker.internal:host-gateway. That's an argparse quirk, not an aibox bug.

aibox init

Merges your template's workspace/ into the current project. This is the only command that writes to your source tree, and it never overwrites without your say-so. See Templates.

FlagArgumentDescription
--templateREFGit URL or local path. Repeatable. Overrides configured templates.
--on-conflictask · skip · replace · keep-bothWhat to do when a file exists and differs. Default ask.
--yes—Non-interactive. Same as --on-conflict skip.
--refresh—Re-clone cached remote templates.
--dry-run—Report the plan, write nothing.

aibox setup

Walks you through configuring your templates and writes ~/.config/aibox/config.toml. It runs automatically the first time you use aibox, so you don't have to know the config file exists.

$ aibox setup

  Welcome to aibox

  Templates seed every project with your own agent guidance —
  a CLAUDE.md, your working practices, your skills — so you don't
  set them up by hand each time.

  Template repo URL or local path (Enter to skip): https://github.com/you/claude-starter

  Fetching…
    workspace/  3 file(s)  → merged into your projects
    home/       1 file(s)  → loaded into the container
  Added.

  Another template (Enter to finish):

  Saved to /home/you/.config/aibox/config.toml

It checks the layout as it goes. If a template has neither a workspace/ nor a home/ directory it would silently do nothing, so aibox says so, shows the expected structure, lists what it found at the top level instead, and links back to this page. You can still choose to use it.

Run it again any time to change your templates. It needs a terminal; to configure aibox in a script, write the config file directly.

aibox info

Prints everything aibox derived for this directory, without starting anything. Useful for checking which volumes belong to a project before deleting them.

$ aibox info

Project path:   /home/you/projects/my-app
Project ID:     my-app-a1b2c3d4
Container:      aibox-my-app-a1b2c3d4-20260815-105908-7f21dd
Image:          aibox-default:latest
Home volume:    aibox-home-my-app-a1b2c3d4
Tmp volume:     aibox-tmp-my-app-a1b2c3d4
Var tmp volume: aibox-var-tmp-my-app-a1b2c3d4
Opt volume:     aibox-opt-my-app-a1b2c3d4
Git access:     commit (history visible, agent can commit; hooks + config frozen)

The project ID is the folder name plus an 8-character hash of its absolute path, so two folders with the same name never share state, and moving a project gives it a fresh set of volumes.

aibox remove-volume

Deletes the four persistent volumes for the current project only. Other projects are untouched. Prompts unless you pass --force.

FlagDescription
--forceSkip the confirmation prompt.

Use it when an agent has made a mess of its own environment, or to reclaim disk. Your project files are not affected — they live on your host, not in the volumes.

aibox rebuild-image

Rebuilds aibox-default:latest. All projects share this image, so a rebuild affects every box. Run it after changing the Dockerfile, or after upgrading aibox if the image contents changed.

Project config: .aibox.toml

Optional, lives in the project root. aibox never creates it for you.

ports = ["3000:3000", "8000:8000"]

env = ["NODE_ENV=development"]

env_files = [".env"]

shell = "/bin/bash"

# "commit" (default) | "readonly" | "masked"
git = "commit"

# overrides your user-level list; [] opts this project out
templates = ["https://github.com/you/claude-starter"]

docker_args = ["--add-host=host.docker.internal:host-gateway"]

How CLI flags compose with it:

  • List fields (ports, env, env_files, docker_args) — the CLI appends to the config values.
  • shell and git — the CLI flag overrides the config.
  • templates — replaces the user-level list entirely. [] means "no templates here".
  • user — CLI only; there is no config key.

Unknown keys and wrong types are rejected with a single-line error, so a typo like port = tells you rather than being silently ignored.

User config

Settings that belong to you rather than to a project live in ~/.config/aibox/config.toml (or $XDG_CONFIG_HOME/aibox/config.toml, or %APPDATA%\aibox on Windows).

templates = [
  "https://github.com/you/claude-starter",
  "~/dotfiles/aibox-template",
]

Cached template clones and staged seeds go under ~/.cache/aibox/.

Git access

By default the agent can read your commit history and make commits and branches. An agent that shapes its work into a clear sequence of commits produces something you can review, and reading history tells it the project's conventions.

ModeThe agent canUse when
commit (default)read history, commit, branch, rebaseyou want the agent to author its own history
readonlyread history onlyyou want it to have context but will commit yourself
maskednothing — .git appears emptya repo you don't want touched at all

What no mode allows

Two things stay locked down even in commit mode, because Git runs them on your machine, as you, the next time you use it:

  • .git/hooks/ is covered by an empty tmpfs. The agent can't leave a pre-commit hook that fires when you next commit from your editor.
  • .git/config is re-mounted read-only. It can name commands through core.pager, core.sshCommand, filter.*.clean, diff.*.textconv and more.

Both extend to submodule git directories under .git/modules/. The protection is the mount, not file permissions: writes land in throwaway container memory and never reach your disk.

The visible side effect is that git config and git remote add fail inside the container. The agent can still write its own ~/.gitconfig, which lives on the project's home volume.

Commit identity

Your global ~/.gitconfig isn't mounted, so when a repo names no identity of its own, commits are attributed to aibox agent <agent@aibox.local>. That also makes sandbox commits obvious in git log. Override it:

$ aibox run -e GIT_AUTHOR_NAME="Your Name" -e GIT_AUTHOR_EMAIL=you@example.com

Where protection actually lives: the agent has no credentials and no gh, so it can't push. Keeping shared history safe is the remote's job — use branch protection rules. A bad local commit is recoverable from the remote or the reflog.

Templates

If every project of yours wants the same agent guidance, keep it in one template repo and seed from it.

# ~/.config/aibox/config.toml
templates = [
  "https://github.com/you/claude-starter",
  "~/dotfiles/aibox-template",     # local paths work too
]

Templates apply in order, so you can layer a general starter with a language-specific one.

Layout

A template has up to two top-level directories, treated very differently:

your-template/
├── workspace/          → merged into your project by `aibox init`
│   ├── CLAUDE.md
│   ├── claude-best-practices.md
│   └── .aibox.toml
└── home/               → synced into the container on every `aibox run`
    └── .claude/skills/
  • workspace/ is repo guidance. It gets committed, so collaborators and agents running on your host see it too. Because it's your source tree, aibox init never overwrites without asking and aibox run never touches it.
  • home/ is your personal agent tooling. It lands on the container's per-project home volume, where an agent picks it up as ~/.claude/skills/, and it never appears in your repo. That volume is disposable aibox state, so it refreshes every run without asking.

Both are optional; a template can provide just one.

First run, and being offered the import

The first time you use aibox with no user config, it runs aibox setup for you and asks for a template.

After that, when you start a box in a project that doesn't have your template files yet, aibox offers to add them:

  This project doesn't have your template files yet.
  3 file(s) would be added. Nothing existing is overwritten.
  Import them? [Y]es  [n]ot now  [never]:

not now asks again next time. never records that choice for this project only, in ~/.local/state/aibox/projects.json — delete that file to be asked again. The offer never appears when there is nothing new to add, when you have no templates configured, or when there is no terminal, so scripted runs are unaffected.

The built-in agent briefing

Every box is seeded with an orientation document at ~/.claude/CLAUDE.md, which agents read as user-level memory. There is nothing to configure — it is always present.

It exists because an agent's default assumption is that your machine is its machine. Without it, agents waste turns searching for an SSH key you mentioned, retrying git push against a remote they cannot authenticate to, or trying to "fix" a read-only .git/config. The briefing covers:

  • Where it is — a disposable container, /workspace as a live mount of one real project, and which paths persist.
  • That your machine is not its machine — if you say your key is at ~/.ssh/id_ed25519, that file genuinely isn't there. It's told to say so plainly rather than hunt for it or ask you to paste a secret.
  • What won't work and why — git push, gh, git config, .git/hooks, apt-get, including that the Git restrictions are host protections rather than bugs to route around.
  • What it can do — commit and branch freely, clone public repos, install packages, drive Chromium.
  • Hard rules — never attempt to escape the sandbox, never modify files outside /workspace, never work on another repository, never push to main or master, and never try to defeat a protection. A blocked action is a boundary to report, not an obstacle to work around.

Overriding it: a template that provides its own home/.claude/CLAUDE.md replaces the briefing entirely. If you do that, carry the guidance across.

Updating a template

Remote templates are cloned into ~/.cache/aibox/templates/ and reused, so aibox run isn't hitting the network every time you start a box. The cache expires after 24 hours, after which the next command re-fetches — so pushing a change to your template repo reaches new boxes within a day without you doing anything.

To pick up a change immediately:

$ aibox run --refresh     # re-fetch, then start the box
$ aibox init --refresh    # re-fetch, then merge into this project

aibox setup always fetches fresh, since you're actively configuring templates and a stale report would be misleading.

Local path templates are never cached. They're read in place, so edits apply on the very next run with no refresh at all — which makes a local path the easiest way to iterate on a template before pushing it.

Offline: a failed fetch is not an error when there's a cached copy. aibox warns, uses what it has, and starts the box. It re-clones into a staging directory and swaps on success, so a failed update can never leave you with a half-written template.

Conflicts

New files are created. A file that already exists and matches is reported unchanged and left alone. A file that exists and differs is a conflict:

  CLAUDE.md already exists and differs.
    [k] keep mine  [r] replace  [b] keep both  [d] diff >

keep both writes the template's copy as CLAUDE.aibox.md so you can merge by hand. When stdin isn't a terminal, aibox keeps your files and says so rather than hanging on a prompt nobody can answer.

Files you choose to keep are reported again next time, because they still differ from the template. Use --yes if you'd rather not hear about it.

Templates are a trust boundary. A template can carry a .claude/settings.json with hooks, which run in your host agent sessions once committed. Fine for your own template repo; think twice about someone else's.

Browser testing

An agent can check its own front-end work by driving a real browser and looking at the result.

The image carries Chromium's system libraries — the part that needs root, and therefore can't be installed from inside the container. The browser itself installs on demand:

$ npx playwright install chromium   # once per project
$ npm install playwright

Then the loop is: navigate, screenshot into /workspace, read the image back.

const { chromium } = require('playwright');
const browser = await chromium.launch();          // headless
const page = await browser.newPage();
await page.goto('http://localhost:3000');
await page.screenshot({ path: 'screenshot.png' });

No GUI is involved, and none is needed. Agents see by reading image files. To look at the app yourself, publish its port with ports = ["3000:3000"] and open it in your own browser.

  • Browsers cache to ~/.cache/ms-playwright on the project's home volume, so the download happens once per project.
  • Chromium only. Firefox and WebKit need their own system libraries, which aren't installed.
  • Heavy pages can exhaust Docker's default 64 MB /dev/shm. Playwright already passes --disable-dev-shm-usage; if you still see crashes, add docker_args = ["--shm-size=1g"].

Mounts and volumes

HostContainerKind
current directory/workspacebind mount, live
aibox-home-{id}/home/devnamed volume
aibox-tmp-{id}/tmpnamed volume
aibox-var-tmp-{id}/var/tmpnamed volume
aibox-opt-{id}/optnamed volume

What persists: those four volumes. Agent config and memory, shell history, npm globals, and anything installed into /opt.

What doesn't: everything else. The container runs with --rm, so changes to /etc, /usr and /lib vanish on exit. Persistent system changes belong in the Dockerfile.

What's in the image

Base python:3.12-slim (Debian 13), with a non-root dev user.

  • Node.js from the official distribution, pinned by the NODE_VERSION build arg and checksum-verified. Debian ships v20; Claude Code needs node >=22.
  • Chromium system libraries via Playwright's own install-deps, pinned by PLAYWRIGHT_VERSION.
  • Tools: bash, curl, git, jq, ripgrep, fd-find, vim, nano, unzip, xz-utils, build-essential, gosu.
  • Not installed: the GitHub CLI (gh), and no credentials of any kind.

git is present because agents legitimately need it — cloning public repos, installing agent plugins and marketplaces. Safety comes from the absent credentials and the frozen Git config, not from withholding the binary.

Security model

What aibox guarantees:

  • No host home mount. ~/.ssh, ~/.aws, ~/.dbt, profiles.yml, warehouse credentials, GitHub tokens — none are reachable.
  • No Docker socket. The container can't talk to the daemon running it.
  • No host code execution. .git/hooks and .git/config are frozen in every Git mode.
  • Non-root user matched to your host UID and GID.
  • Writes confined to the project. Only /workspace maps to your filesystem.

What it explicitly does not protect against:

  • Anything inside /workspace. The agent can delete or rewrite your project files. That's the job you gave it.
  • Local Git history under --git commit. Resets and rebases are intended behaviour; the remote plus branch protection is the safety net.
  • Network egress. Outbound traffic is currently unrestricted.

Report anything that breaks the guarantees above through GitHub security advisories.

Troubleshooting

"Permission denied connecting to the Docker daemon"

On Linux you're not in the docker group. Run sudo usermod -aG docker $USER, then start a new login session — a new terminal tab is not enough, the group set is fixed at login.

"Docker is not running"

Start it: sudo systemctl start docker on Linux, or launch Docker Desktop.

A command works in the container but not under bash -l

Should be fixed — /etc/profile.d/aibox-path.sh restores the user-local tool paths that /etc/profile would otherwise overwrite. If you see it, rebuild with aibox rebuild-image.

Chromium fails with "Target page, context or browser has been closed"

The real error is usually a missing shared library, buried in the browser log. Rebuild the image — Chromium's system libraries were added in a later version.

Changes to the Dockerfile or entrypoint have no effect

Run aibox rebuild-image. Existing images are never rebuilt automatically.

The agent lost everything it installed

Only /home/dev, /tmp, /var/tmp and /opt persist. Anything installed elsewhere goes away with the container.

Limitations

  • Podman is not supported. Rootless UID mapping, SELinux labelling and tmpcopyup all differ from Docker in ways that would silently unmask .git.
  • Egress is unrestricted. A compromised agent can reach the network freely. A proxy-based allowlist is on the roadmap.
  • One shared image. Every project uses aibox-default:latest; custom images per project aren't supported yet.
  • No Docker Compose. Projects needing sidecar services aren't covered.
  • Symlinked project directories are untested across platforms, particularly Windows junction points and WSL-to-Windows paths.
  • Linked worktrees. When .git is a file rather than a directory, the real git dir lives outside the project and isn't mounted, so Git access modes don't apply.
